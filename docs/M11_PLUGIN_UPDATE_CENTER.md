# M11 — 插件更新中心实施计划

## 目标

在 FR ComfyUI Control Center 的实例设置中增加“插件”页，让用户无需进入
ComfyUI 画布即可查看自定义节点状态、检查 Git 更新，并在受管环境中执行更新。
同时覆盖手动 `git clone` 到 `custom_nodes` 的插件，以及由 Manager v4 / Comfy Registry
安装并通过 `.tracking` 与 `pyproject.toml` 标识版本的 CNR 软件包。

## 边界与原则

- ComfyUI-Manager 以 **v4** 为唯一后端事实来源；更新执行使用当前实例中的
  `cm_cli` / `comfyui_manager` v4 引擎，不依赖旧版 v3 的 `/customnode/*` 接口。
  控制中心通过一个很薄的适配器传入 `instant_execution=True`，确保 Windows 上的
  CNR 文件切换与依赖安装在本次更新事务内完成，而不是延迟到下次启动。
- Git 更新检查是控制中心的只读探测：读取分支、上游、工作区状态、提交差异；
  CNR 更新检查读取安装版本，并通过 Comfy Registry（失败时回退 Manager v4 缓存）
  获取最新版本。
  受管环境按需 fetch；Stable/read-only 环境只用 `ls-remote` 查询远端，不写入其
  `.git` 元数据。检查过程不启动 ComfyUI，也不修改插件工作树。
- `C:\FR_comfyui`（Stable）始终为只读观察对象：允许扫描和检查，禁止从控制中心更新。
- 已登记为 `read-only` 的环境禁止更新；Next/Lab 只有在环境注册表中为
  `managed` 时才允许更新。普通由控制中心创建且不属于 FR 保留路径的实例按原有
  安装记录授权管理。
- 更新插件是独立事务，不顺带升级 Python、PyTorch、CUDA、Triton、xFormers、
  TensorRT 或 ComfyUI Core。
- 更新前必须停止实例并保存 `pre-update` 快照与完整插件目录备份；失败时保留快照和
  完整日志，恢复源文件、Git 元数据及更新前的用户文件，清除本次更新留下的部分新文件。

## 第一版交付范围

### 1. 只读库存与更新检测

每个插件展示：

- 名称、目录名、启用状态、来源类型（Git / CNR / 手动安装 / file）；
- 远程仓库、当前分支、上游分支；
- 本地与远程提交短 SHA；
- ahead / behind 数量；
- 工作树是否有未提交改动；
- CNR 已安装版本与注册表最新版本；
- `已是最新`、`有更新`、`本地领先`、`已分叉`、`游离 HEAD`、`无上游`、
  `网络不可达`、`需手动更新` 等明确状态。

插件页先读取本地 Git 引用、Manager v4 缓存和控制中心短时缓存，立即绘制库存；随后
在后台刷新 Registry 与 Git。用户点击“重新检查”时强制刷新。一个仓库失败不会阻断
其他仓库的结果。

### 2. 更新事务

用户可选择单个或多个处于 `有更新` 状态的插件。执行顺序：

1. 校验实例管理权限、实例已停止、选择项仍存在；
2. 重新检查工作树，拒绝 dirty / diverged / detached / no-upstream；
3. 保存控制中心 `pre-update` 快照，记录每个插件原始提交；对选中的 Git/CNR 插件额外
   复制到实例 `.launcher/plugin-update-backups/<transaction>/`，形成不依赖网络的
   本地源文件恢复点；
4. 向当前实例 Python 中的 Manager v4 即时更新适配器传入 `--plugin-dir` 安装路径。
   适配器根据规范化真实路径唯一匹配 Manager 的已安装记录，并验证对应 active 更新表。
   已注册 Git 插件使用真实 ID 与 `nightly`，未注册 Git 插件使用 Manager 识别的 ID 与
   `unknown`，CNR 使用真实 ID 与实际已安装版本；路径越界、停用、身份缺失或记录冲突
   在源码更新前明确报错。更新后的 Manager 状态检查复用相同路径解析，并校验 CNR 目标版本；
   Windows 更新进程通过 `GIT_CONFIG_COUNT` 追加 `core.longpaths=true`，继承到 Manager 的
   Git 子进程，不修改全局 Git 配置、仓库配置或系统注册表。Git 更新传入精确目标提交，
   在依赖及安装钩子前检查 HEAD 和工作树，拦截 Manager v4 未传播子进程失败的情况；
5. 解析每个插件的退出状态与错误输出，随后重新扫描 Git 提交或 CNR 版本；
6. 成功后保存 `post-update` 快照、提交逐项结果并清理备份；失败时从本地备份恢复完整
   Git/CNR 目录和完整 Python 环境，依赖恢复不需要网络。恢复失败时保留日志及备份并阻止启动。
7. 普通更新与兼容性更新结束后都保持实例停止，由用户手动启动；失败及重试不会自动启动。

第一版不自动替用户合并本地改动、切换分支或解决冲突。

### 2.1 含编译依赖插件的兼容性入口

含编译依赖的插件继续禁止进入普通批量更新，但在同一插件页提供独立的“检查兼容性”
入口。检查阶段将精确目标 CNR 版本或 Git commit 暂存到系统临时目录，只做静态分析，
不导入目标插件代码，也不改动实例工作树。报告包括：

- Python 版本/架构、Torch/CUDA、NumPy 与已安装编译包指纹；
- 当前与目标的 requirements / `pyproject.toml` 依赖差异；
- `install.py`、`setup.py`、批处理/脚本与启动钩子变化；
- `.pyd`、`.dll`、`.so` 等原生文件变化；
- Manager v4 实际 `config.ini`、监听地址与 CNR/Git 风险级别的策略结果；
- 阻止项、需人工确认项、已有环境问题和可执行结论。

依赖声明通过目标 Python 的 `packaging.Requirement` / `SpecifierSet` 判断，解析 PEP 508
markers、extras 和 PEP 440 版本规则；requirements 的文件内包含只能留在插件目录。
同名、同 extras 和同适用性的重复声明合并；声明变化与实际包安装分开计数。删除声明不会
自动卸载已有包。pyproject 动态依赖、URL 依赖及未识别的 pip 选项转入单独审核。

更新分为四条路径：

- **仅更新源码**：目标的活动依赖及已选 extras 已满足，没有变更的安装钩子或原生文件。
  即使声明有变化也可执行。普通批量更新同样先预检，只接受这一类计划。
- **待确认依赖方案**：通过真实 uv 解析和 wheel 元数据检查生成具体版本、直接/间接原因、
  文件来源、兼容标签、SHA256、下载量和环境备份量。保留现有包并约束其已满足的依赖，
  允许解析器回退选择兼容版本；只从 PyPI 获取 wheel，不构建源码包。
- **需单独审核**：变更的安装钩子/原生文件、动态声明及尚无验证配置的 GPU/特殊运行库。
  当前不提供强制执行按钮，Lab 自动验证属于后续里程碑。
- **阻塞**：受保护栈不满足、其他已安装包冲突、缺少兼容 wheel、来源或 Manager v4 策略
  不允许。报告展示具体依赖边及版本约束，解析器原始输出折叠展示。未允许 pip 安装时仍可
  做只读解析，但不能确认执行依赖变更，不会自动修改 Manager 设置。

执行请求绑定精确目标、源码文件哈希、全部安装包/依赖元数据/markers 环境、计划摘要和
十分钟有效期。主进程要求原始缓存中存在未过期计划，重新解析检查摘要，准备并验证 wheel，
在源码更新前再次检查插件文件。版本、来源或环境变化拒绝旧确认。

两种更新均保存完整插件目录及托管 `ComfyUI/.venv` 的独立副本，备份前检查可用空间。
导入验证会执行插件代码，因此仅更新源码也备份完整环境，避免导入副作用绕过恢复。
外部共享 Python 环境不进入此更新流程。编译验证缓存按实例和计划摘要隔离。

所有源码更新都经 Manager v4 `no_deps` 路径完成，明确跳过 post-install 回调。
获批的依赖以本地 wheel、`--offline --no-index --no-deps --no-build --require-hashes`
及 `--link-mode copy` 安装，不临时扩大升级/卸载范围或依赖外部缓存。

更新后校验精确源码版本、完整 Python 包状态、受保护栈、相对基线新增的 `pip check`
问题、插件导入和 Manager v4 识别状态。插件导入使用 ComfyUI 原生单插件加载器，并先创建
不监听端口的 `PromptServer` 上下文，避免把依赖 `PromptServer.instance` 注册路由的正常插件
误判为失败；不会发现或导入其他自定义节点。任一步失败或 post-update 快照无法提交，都会
恢复 Git/CNR 源码与事务前完整 Python 环境。导入和 Manager 验证后再次检查包状态及
新增依赖问题，避免成功导入过程中的自动安装被遗漏。

事务日志 `.launcher/plugin-update-in-progress.json` 在源码和依赖改动前持久化阶段：
prepared → applying-source → applying-dependencies → validating → committed。更新、恢复、
环境修改或启动前先处理遗留日志；实际恢复后保持停止并提示用户重新检查。失败恢复保留
唯一备份并阻止继续修改。committed 日志仅清理，不撤销已经提交的更新。恢复路径检查
拒绝目录链接、越界及无效备份，避免触及 Stable 或共享模型库。

### 3. 界面

- 在实例设置中增加“插件”页，仅对本地实例显示；
- 顶部显示总数、可更新数、需处理数和最近检查时间；
- 支持搜索、筛选、全选可更新项、更新所选、更新全部；
- 插件更新操作栏作为搜索区下方、列表上方的普通卡片显示，不覆盖实例级“启动 ComfyUI”
  底栏，也不需要滚到长列表末尾；普通可更新插件行还提供直接“更新”按钮；
- 搜索框与固定宽度筛选器在宽屏同排、窄屏堆叠，避免筛选器挤压搜索输入；
- 含编译依赖的更新行显示独立兼容性按钮与结构化报告，不混入普通批量选择；
- 只有缺少 Git 与 CNR 跟踪信息的目录才显示“需手动更新”，原因文本完整本地化；
- 每行可展开更新详情，显示来源、目录、仓库、当前/目标版本、上游和依赖钩子；
- 最近一次批量更新按插件显示“已更新 / 已回滚 / 失败 / 未执行”；进度页也为每个
  插件显示独立步骤；
- Stable / read-only 环境显示清晰的只读提示；
- 更新复用现有进度与日志界面，完成后重新检查。

## 验收标准

- 合成 Git 仓库能够稳定识别 up-to-date、behind、ahead、diverged、dirty、
  detached、no-upstream；测试不访问公网。
- 手动 Git 插件不依赖 Registry 元数据也能显示更新状态。
- Stable 和 read-only 环境的主进程执行入口均 fail closed，不能只靠按钮禁用。
- 运行中的实例不能进入更新事务。
- 更新前后均生成快照；失败日志能指出插件和 Manager v4 输出。
- CNR 更新在断网条件下仍可从事务前的本地目录备份回滚。
- Windows 超过 260 字符的工作流路径能通过真实 Git 子进程写入；失败时不执行依赖
  安装，完整目录回滚同时恢复 Git 元数据和用户文件，移除部分写入的新增文件。
- 插件页首次绘制不等待远端请求，后台刷新完成后原位更新状态。
- 含编译依赖插件的预检不执行插件代码；过期计划、受保护栈变更和缺失编译依赖均
  fail closed；预存环境问题与更新新引入的问题分开报告。
- 兼容性事务不得产生非计划包变化；失败时源码和依赖均回滚，成功时记录计划摘要与
  各项验证结果。
- `pnpm run typecheck`、相关 Vitest 单元/组件测试通过。
- Python 适配器回归测试通过标准库 unittest 执行，使用临时目录与 Manager v4 记录替身，
  不访问公网、不导入插件、不操作真实安装。集成测试可用 `FR_TEST_PYTHON` 指定具有完整
  标准库的测试解释器（发行包 bootstrap Python 是裁剪版，不用于此测试）。
- 运行中和已停止实例的两种插件更新，成功、失败及重试后均保持停止。

## 本轮实测记录（2026-10-04）

读取现有 Next 的依赖元数据及 CNR `comfyui_controlnet_aux@1.1.6` 归档，只做解析，
没有安装或导入目标插件。实际缺失包为 `albumentationsx`。保留已安装依赖时，
`albumentations` 要求 `albucore==0.0.24`，解析器的候选 `albumentationsx` 要求
不同的 albucore 版本，回退尝试仍无可用方案。目标 pyproject 还声明了 albumentations。
此实例应报告具体冲突并阻塞；不能把声明差异直接当成可安全安装方案或自动替换共享包。

离线回归包括 marker/extras、版本、递归声明、CUDA 本地版本保留、间接依赖、反向冲突、
兼容候选回退、无 wheel 拦截、哈希与来源、真实临时 venv 离线安装、完整环境恢复、
中断阶段恢复、确认/过期校验及导入后的包漂移检测。测试解释器通过 `FR_TEST_PYTHON`
指定，uv 通过 `FR_TEST_UV` 指定，所有安装测试仅使用临时环境。
